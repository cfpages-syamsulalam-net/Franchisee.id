# Franchisee.id: what to do next

Reviewed 24 September 2026. Read [user journeys](USER_JOURNEYS.md) first. This is a decision and verification queue for the current codebase, not a promise that code paths already work in every production account. `P0` means protect ownership or prove a core path before expanding traffic; `P1` means close a known operational gap; `P2` means improve acquisition once the core paths are sound. The order below is intentional.

## Start here: three decisions for Syamsul

1. **Brand claims:** adopt the documented rule that a claim stays `pending` and grants no owner control until an admin verifies it. The [claim transition matrix](../forms/CLAIM_TRANSITION_MATRIX.md) says this; current submit code does something else. Prioritize a controlled repair before inviting owners to claim brands.
2. **Test identities:** designate one franchisee test account, one franchisor test account, and staff/admin testers, plus a disposable listing and an explicitly approved test payment method. Keep real customer claims and real money out of the initial walk-through.
3. **Claim scope and homepage count:** decide whether the homepage's `500+ Brand Franchise` refers to this site's directory or the wider network. The D1 static snapshot used by this directory contained 197 listings at this review; use a sourced scope/date label or remove the count if it cannot be substantiated.

## A short production walk-through

Use a disposable record and keep a dated result (pass/fail/not run) for each row. This is a manual acceptance script, not evidence that those flows have already passed.

| Who | Action | Expected evidence |
| --- | --- | --- |
| Guest buyer | Filter `/peluang-usaha` by category + kota + modal; open a listing, compare, use Budget & BEP; try save/contact without a session. | Shareable URL preserves filters; zero-result/reset works; sign-in prompt preserves the intended listing; unclaimed data is labeled. | Franchisee member | Register/login with email or Google, complete `/daftar`, open `/profil` → Peluang Saya, save a listing, send an inquiry, reload. | D1 role and profile are correct; save survives reload; inquiry appears in buyer history and only the relevant owner inbox; denial/duplicate feedback is clear. |
| New franchisor | Add franchisor role if necessary, submit `/daftar`, edit/upload one listing in `/profil`, receive/update a test lead. | Listing belongs to this user only; upload URL works; queue and public detail update; no access to another owner's brand/lead. |
| Claimant and admin | Once claim logic is repaired, submit a claim for a disposable unclaimed row; attempt conflicting claim; approve/reject from Review. | Claim stays pending before review, evidence is available, only admin approval applies owner, rejection is non-destructive, public change follows rebuild. |
| Staff | Open Outreach, connect a test Google Contacts account if needed, save one contact, open WhatsApp, explicitly confirm the sent step, move the pipeline card, suggest an edit. | Contact result is confirmed by API, opening WhatsApp alone does not mark sent, pipeline and Review reflect actions, staff cannot self-approve without a deliberate admin rule. |
| Admin/Premium owner | Create/confirm a controlled Premium order, inspect Review/Premium and Publication/System, resolve payment, confirm owner/public state. | No duplicate order or ownership leak; subscription, listing tier, outbound notice, queue and public badge agree. |

**Working rule:** record one failed step with its persona, account role, route, exact action and sanitized response; fix its root cause and rerun that journey before adding more features.
