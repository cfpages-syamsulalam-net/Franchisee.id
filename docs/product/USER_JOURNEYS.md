# Franchisee.id user journeys

Reviewed 24 September 2026 against the repository at `1646f3a`. This is a guide to the behavior implemented in code, not a claim that every signed-in or payment step has been tested in production. Start with [what to do next](NEXT_STEPS.md); the underlying product plans are linked below.

A member can add the other public role through `/profil` (`add_public_role`); role badges in the browser are hints, while D1 authorization is the server boundary. An unclaimed brand's listed city is a recorded location, not a promise that the brand is accepting partners there. A franchisee buyer and a franchise owner are distinct personas even when the same account has both roles.

## Follow the handoffs

1. **Discover → decide:** the visitor filters the directory, opens a listing, compares costs and information, and chooses save, contact or claim. Check whether the brand and modal claims are supported by the listing data; details and contact data on an unclaimed profile are not owner-verified (`src/lib/franchise-static.ts`, `src/lib/franchise-buyer-tools.ts`).
2. **Identity → completion:** Clerk creates/authenticates the account; `/auth-sync` maps it to D1 roles; `/daftar` completes role-specific information. `/profil` shows the useful next action, existing account information and role-specific work. Never interpret signing up alone as a completed buyer profile or a published brand (`js/auth-clerk.js`, `functions/auth-sync.js`, `functions/form-submit.js`, `functions/profile-data.js`).
3. **Interest → lead → response:** a signed-in buyer saves or sends an inquiry; the owned franchisor listing's lead inbox and dashboard Leads expose follow-up work. Confirm that the inquiry is visible to the intended owner, has actionable contact details and has a recoverable duplicate/denied state (`functions/profile-data.js`, `js/profile-leads.js`, `functions/_dashboard-queries.js`).
4. **Brand update → public page:** a form submission, permitted owner edit or admin approval writes D1 and enqueues `site_rebuild_requests`. A queue poller/Deploy Hook rebuilds public Astro pages. An API success does **not** prove that the public page changed (`functions/_site-publish-queue.js`, `.github/workflows/d1-static-publish.yaml`, `scripts/build-d1-franchise-pages.ts`).
5. **Premium order → decision → renewal:** an owner creates a manual bank-transfer order from `/profil`, uploads/records payment confirmation, admin reviews in `/dashboard`, subscription/placement updates and public rebuild follow; scheduled reminders and expiry handling are separate. Avoid calling a payment complete until the order, subscription and public state agree (`functions/_profile-premium.js`, `functions/_dashboard-actions.js`, [Premium plan](../architecture/PREMIUM_MONETIZATION_PLAN.md)).
6. **Claim → review → ownership:** the intended product rule is pending claim, evidence review, then ownership/publication on approval ([claim matrix](../forms/CLAIM_TRANSITION_MATRIX.md)). The current submit implementation differs; do not use this path as proof of brand ownership until priority 1 is resolved.
